# 시장 대시보드 배포 검증

## 원칙

- 검증을 시작하기 전에 [references/korea-market-dashboard.md](references/korea-market-dashboard.md)를 끝까지 읽고 현재 저장소 내용과 함께 적용한다.
- 저장소 루트에서 아래 다섯 영역을 순서대로 읽기 전용 검증한다.
- 파일·코드·설정·Git 이력·Vercel 상태를 수정하지 않는다. 자동 수정, 커밋, push, 배포·재배포, 캐시 무효화, 환경변수 조회·변경을 하지 않는다.
- 환경변수는 이름만 다룬다. 로컬 환경 파일이나 Vercel 설정에서 값을 읽거나 출력하지 않는다.
- Vercel 관련 정보는 연결된 Vercel MCP의 읽기 도구만 사용한다. Vercel CLI, `curl`, 일반 웹 검색·브라우저, 별도 API 호출을 사용하지 않는다. 도구를 설치하거나 로그인하지 않는다.
- Vercel MCP에서는 프로젝트 탐색과 검증에 필요한 `list_teams`, `list_projects`, `get_project`, `list_deployments`, `get_deployment`, `web_fetch_vercel_url`, `get_runtime_errors`, `get_runtime_logs`만 사용한다. 쓰기·구매·배포·임시 접근 링크 생성 도구를 호출하지 않는다.
- 확인할 수 없는 사실을 추정하지 않는다. MCP 미연결, 권한 부족, 응답 누락, 검사 실패는 PASS가 아니라 WARNING으로 기록하고 사람이 확인할 구체적인 위치와 방법을 안내한다.
- 근거에 비밀값, 인증 헤더, 임시 접근 토큰, 전체 환경변수 값을 포함하지 않는다.

## 1. 배포 상태

1. 사용자가 공유 대상 커밋을 지정했으면 그 전체 SHA를 사용하고, 지정하지 않았으면 현재 `HEAD`의 전체 SHA를 사용한다.
2. 현재 브랜치와 작업 트리 상태를 읽는다. 미커밋 변경이 있으면 비교 자체는 대상 SHA로 계속하되 공유 대상이 불명확하므로 이 영역을 최소 WARNING으로 판정한다.
3. Vercel MCP로 팀과 프로젝트를 찾고, 생성 시각 기준 최신 프로덕션 배포를 고른다. 프로젝트가 둘 이상으로 모호하면 추측하지 않는다.
4. 배포 상세에서 프로덕션 대상, 상태, 생성 시각, 배포 URL, Git 커밋 SHA를 확인한다.
5. 최신 프로덕션 배포가 Ready이고 배포 SHA가 대상 SHA와 정확히 같을 때만 이 조건을 PASS로 본다.

판정한다.

- Ready가 아니거나 SHA가 다르면 BLOCKED로 판정한다.
- 배포나 커밋 메타데이터를 확인할 수 없으면 WARNING으로 판정한다.
- 근거에는 대상 SHA와 배포 SHA를 짧게 표시하되 서로 비교할 때는 전체 SHA를 사용한다.

## 2. 배포 화면·API

1. 1단계에서 확정한 최신 프로덕션 주소의 루트 경로를 Vercel MCP의 `web_fetch_vercel_url`로 직접 연다.
2. 앱 reference의 화면 완료 기준에 따라 응답 상태, 데이터 출처, 기준일, 실제 시세와 각 화면 영역을 확인한다.
3. 이 앱에는 별도 공개 API 라우트가 없으므로 임의의 API 주소를 만들지 않는다. 루트 화면의 서버 렌더링 결과가 실제 외부 시세 조회 결과임을 확인한다.

판정한다.

- 페이지 오류, 예시 데이터 표시, 기준일 누락·허용 범위 초과, 필수 시세 영역 누락·비정상 값은 BLOCKED로 판정한다.
- Vercel MCP 응답만으로 필수 내용을 확인할 수 없으면 WARNING으로 판정하고 사람이 프로덕션 주소에서 확인할 항목을 적는다.
- 모든 화면 기준을 확인했을 때만 PASS로 판정한다.

## 3. 런타임 로그

1. 최신 프로덕션 배포와 프로젝트를 대상으로 최근 24시간을 검사한다.
2. `get_runtime_errors`로 오류 군집과 발생 횟수를 먼저 확인해 조사 후보를 찾는다.
3. `get_runtime_logs`에서 `environment=production`, 최신 배포, `statusCode=5xx`를 지정해 상태 코드와 요청 경로별로 집계한다. 로그 원문에 포함된 민감한 값은 보고서에 옮기지 않는다.
4. 프로젝트 전체 오류 군집은 최신 프로덕션 배포의 5xx 로그로 뒷받침될 때만 실패 근거로 사용한다. 환경이나 배포 범위를 구분할 수 없으면 WARNING으로 남긴다.
5. 같은 경로·상태 코드 또는 같은 오류 군집이 2회 이상 발생하면 반복 오류로 본다.

판정한다.

- 반복되는 5xx가 있으면 BLOCKED로 판정한다.
- 5xx가 한 번만 관찰되면 WARNING으로 판정하고 경로·시각·상태 코드만 요약한다.
- 두 조회가 성공하고 최근 24시간의 5xx가 0건이면 PASS로 판정한다.
- 로그 기능 미지원, 권한 부족, 시간 범위·환경·배포 범위 확인 실패는 WARNING으로 판정한다.

## 4. 환경변수 계약

1. Git 추적 대상인 애플리케이션 소스에서 런타임이 요구하는 환경변수 **이름만** 수집한다. 점 표기뿐 아니라 대괄호 표기, 문자열 상수, 헬퍼 함수로 전달되는 동적 접근까지 추적한다.
2. 샘플 계약 파일에서는 등호 왼쪽의 이름만 추출하고 값을 읽거나 출력하지 않는다.
3. 앱별 기준 문서에서는 환경변수 이름과 필수 여부만 확인한다.
4. 코드 요구 이름, 샘플 계약 이름, 앱별 문서 이름을 각각 정렬해 비교한다. reference에 적힌 현재 계약 위치를 사용하되 실제 파일의 최신 내용을 기준으로 한다.

판정한다.

- 코드가 요구하는 이름이 샘플 계약이나 필수 앱 문서 중 하나라도 빠져 있으면 BLOCKED로 판정한다.
- 두 계약 문서가 서로 다르거나 계약에만 남은 이름이 있으면 WARNING으로 판정한다.
- 계약 파일을 읽을 수 없어 비교가 불완전하면 WARNING으로 판정한다.
- 세 집합이 일치할 때만 PASS로 판정한다.

## 5. Git 비밀 검사

1. `python3 .agents/skills/verify-market-dashboard/scripts/scan_git_secrets.py --repo .`를 실행한다.
2. 스크립트가 검사하지 못한 blob, 명령 실패 또는 수동 검토 후보를 보고하면 WARNING 근거로 남긴다.
3. 비밀 후보의 실제 값이나 일치한 원문을 다시 열거나 보고서에 복사하지 않는다.

판정한다.

- 현재 Git 추적 파일이나 도달 가능한 커밋 이력에 실제 환경 파일 경로 또는 높은 신뢰도의 비밀 패턴이 있으면 BLOCKED로 판정한다.
- 휴리스틱 후보 또는 검사 누락만 있으면 WARNING으로 판정한다.
- 스크립트가 전체 범위를 검사해 발견 사항이 없을 때만 PASS로 판정한다.

## 전체 판정과 보고

- 한 영역이라도 BLOCKED이면 전체를 BLOCKED로 판정한다.
- BLOCKED가 없고 WARNING이 하나라도 있으면 전체를 WARNING으로 판정한다.
- 다섯 영역이 모두 PASS일 때만 전체를 PASS로 판정한다.
- 보고서는 항상 한국어로 작성하고 아래 형식만 사용한다. 표의 영역 이름과 순서를 바꾸거나 행을 추가하지 않는다.
- 각 근거에 확인 시각 또는 시간 범위, 대상 식별자, 관찰 결과를 짧게 포함한다. PASS의 다음 행동은 `없음`으로 적고, WARNING과 BLOCKED에는 사람이 수행할 구체적인 다음 행동을 적는다.

```markdown
전체 판정: PASS|WARNING|BLOCKED

| 영역 | 상태 | 확인한 근거 | 다음 행동 |
| --- | --- | --- | --- |
| 배포 상태 | PASS|WARNING|BLOCKED | ... | ... |
| 배포 화면·API | PASS|WARNING|BLOCKED | ... | ... |
| 런타임 로그 | PASS|WARNING|BLOCKED | ... | ... |
| 환경변수 계약 | PASS|WARNING|BLOCKED | ... | ... |
| Git 비밀 검사 | PASS|WARNING|BLOCKED | ... | ... |
```
