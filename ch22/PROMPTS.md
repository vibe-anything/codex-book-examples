# 21~22장 프롬프트 모음

아래 요청문은 15~20장에서 이어 온 주식 대시보드의 원래 작업 폴더에서 Codex를 연 뒤, 21장과
22장의 흐름에 맞춰 사용한 기록입니다. 21장에서는 메인 Codex가 Git worktree 두 곳과
subagent 두 명을 준비해 병렬 작업을 관리합니다. 22장에서는 새 세션에 전달되지 않은 결정의
경계를 확인하고 README와 AGENTS.md에 프로젝트 기억을 남깁니다.

이 폴더(`ch22`)는 21장의 종목 비교·다크 모드와 22장의 프로젝트 기억 패키지까지 반영한 완성
스냅숏입니다. 21장을 재현하려면 20장까지 마친 깨끗한 작업본에서, 22장의 before 실험을
재현하려면 문서화 전 ch21 작업본을 별도 폴더에 복사해 시작합니다. 완성 스냅숏에 1번이나
4번 요청을 다시 보내면 이미 끝난 기능과 결정을 다시 바꿀 수 있습니다.

비밀 `.env`, 운영 데이터, 실제 계좌 정보는 Codex 대화나 worktree에 복사하지 않습니다. 예시
데이터만으로 두 기능을 만들고 검사합니다.

## 0. 원래 작업 폴더에서 Codex 열기

`path/to/my-market-dashboard`는 20장까지 작업한 자신의 대시보드 경로로 바꿉니다.

```bash
cd path/to/my-market-dashboard
codex
```

이미 다른 worktree 안에서 작업 중이라면 그곳에서 계속하지 않고 원래 작업 폴더로 돌아옵니다.
추적·미추적 변경이 남아 있다면 임의로 커밋하거나 숨기지 말고 먼저 내용을 확인합니다.

## 1. 두 기능을 worktree에서 병렬로 만들고 합치기

다음 요청 하나로 작업 상태 확인, worktree 생성, subagent 병렬 실행, 검사와 순차 병합까지
맡깁니다.

```text
대시보드에 두 기능을 동시에 만들어줘.

만들 것
- 종목 비교: 서로 다른 두 종목의 일별 종가와 해당 거래일 등락률을 나란히 보여주고,
  선택을 기억한다.
  같은 종목을 고르면 다른 종목을 고르도록 알려준다.
- 다크 모드: 처음에는 컴퓨터 화면 설정을 따르고, 내가 고른 화면 모드를 기억한다.
  모든 카드와 상승·하락 정보는 두 화면에서 또렷하게 보여주고, 색과 부호로 함께 구분한다.

진행
- 먼저 지금 작업을 잃을 위험이 없는지 확인해줘.
- 안전하면 기능마다 별도 git worktree와 subagent 한 명을 배정해 병렬로 구현해줘.
- 각 subagent에게 작업 경로·브랜치·수정 범위를 알려주고, 올바른 작업장인지 확인한 뒤 시작하게 해줘.
- 별도 작업장에 쓸 권한이 없으면 같은 폴더에서 진행하지 말고 멈춰서 알려줘.

완료
- 각 subagent가 맡은 범위만 예시 데이터로 검사해 커밋하게 해줘.
- 둘 다 통과하면 시작점 대비 각 변경을 검토하고 하나씩 합쳐줘. 충돌이나 제품 결정이 필요하면 현재 병합을 중단하고 알려줘.
- 홈과 비교 화면의 두 모드, 기존 기능, 자동 검사와 빌드까지 확인해줘.
- 두 subagent가 실제로 병렬 실행됐는지, 시작 커밋과 최종 결과 사이의 Diff 요약, 최종 주소를 보여줘.
- push·배포·작업장 정리는 하지 마.
```

Codex가 저장하지 않은 변경이나 권한 문제를 발견해 멈추면 그것이 정상입니다. 같은 폴더에서
작업하도록 강행하지 말고, 보고된 문제를 확인한 뒤 안전한 상태에서 다시 요청합니다.

## 2. 합친 제품 직접 확인하기

완료 보고가 오면 최종 주소를 열고 다음 세 묶음을 사람이 직접 확인합니다.

1. 서로 다른 종목 두 개를 고르고 바꿀 수 있는지, 같은 종목을 고르면 다음 행동을 알려 주는지
   봅니다.
2. 홈과 비교 화면을 밝게·어둡게 바꾸고, 새로고침 뒤에도 비교 종목과 화면 모드 선택이 남는지
   확인합니다.
3. 기존 관심 종목과 시장 화면이 그대로 동작하고, 자동 검사와 빌드가 통과했는지 확인합니다.

화면이나 동작이 기대와 다르면 작업장부터 정리하지 않습니다. 같은 메인 Codex 세션에 관찰한
문제를 말하고, 수정 뒤 세 묶음을 다시 확인합니다.

## 3. 최종 확인 뒤 작업장 정리하기

다음 요청은 합친 화면과 변경 사항을 사람이 모두 확인한 뒤에만 보냅니다. 첫 요청에서 작업장을
정리하지 말라고 했으므로, 결과 확인 전에는 이 후속 요청을 보내지 않습니다.

```text
최종 결과를 확인했어. 합친 커밋이 원래 프로젝트에 남아 있는지 다시 확인하고, 이번 작업에 만든 worktree와 작업용 브랜치만 안전하게 정리해줘.
```

정리가 끝나면 원래 프로젝트의 최종 커밋과 Git 상태를 다시 확인합니다. 이번 작업과 관계없는
worktree나 브랜치는 삭제하지 않습니다.

## 4. 문서화 전 새 세션으로 결정의 경계 확인하기

이 단계는 README와 AGENTS.md를 갱신하기 전의 격리된 작업본에서만 실행합니다. `/new`로
지금까지의 작업 맥락을 비운 뒤 다음 요청을 보냅니다.

```text
업종 히트맵에 빠져 있는 업종들이 있네. 채워줄 수 있어?
```

실제 before 실험에서는 조선·게임·2차전지를 공식 TOP 10 테마지수로 추가했지만, 대응 지수를
찾지 못한 화장품까지 대표 6종목의 등락률 평균과 거래대금 합계라는 임의 산식으로 채웠습니다.
총 12개 타일을 만들고 단위 테스트 15개와 빌드도 통과했습니다. 이 결과는 따라 할 정답이
아니라, 테스트 통과만으로 제품 결정의 근거까지 보장할 수 없다는 비교 기준입니다.

## 5. 오늘의 세션에게 프로젝트 기억 패키지 맡기기

`/resume`으로 21장까지의 결정을 아는 원래 대화로 돌아온 뒤 다음 요청을 보냅니다. 비밀값은
읽거나 출력하지 않고, 이 단계에서는 아직 커밋·push·배포하지 않습니다.

```text
이 프로젝트를 다음 사람과 다음 AI 세션이 이어받을 수 있게 문서를 갱신해줘.

먼저 현재 코드, README.md, AGENTS.md, API_CHECK.md, .env.sample을 읽고 서로 어긋난 부분을
확인해줘. .env의 실제 값은 읽거나 출력하지 마.

README에는 사람이 읽을 것을 정리해줘.
- 처음 받은 사람이 설치, 환경변수 설정, 실행까지 가는 3단계
- 다시 이어야 할 Supabase와 Vercel 연결
- 데이터 출처, 일별 시세의 갱신 시점, 휴장일과 기준일
- 시장 열기 계산 기준
- 현재 구현과 저장 경계
- 결정과 이유:
  - 조선·게임·2차전지는 2026-07-19 공식 응답에서 확인한 TOP 10 테마지수만 정확히 매핑하고,
    산업분류 지수처럼 표현하지 않는다.
  - 같은 응답에서 화장품·뷰티·코스메틱에 대응하는 지수를 확인하지 못했으므로 유사 소비재
    지수, 대표 종목 평균, 임의 값으로 대신하지 않는다.
  - 보유 종목·개인 수익률은 실제 계좌 연동 없이는 가짜 숫자라 넣지 않는다.
  - 종목 비교는 한 화면에 나란히 보는 목적이라 두 종목까지만 둔다.
  - '예시 데이터' 안내는 전체 수집 실패를 알리는 표시라 지우지 않는다.
- 알려진 한계, 되돌리는 법, 남은 일

AGENTS.md에는 다음 세션이 지킬 것을 정리해줘.
- 작업 전 README의 결정 기록과 API_CHECK.md의 확인일·근거를 읽는다.
- 코드를 바꾸면 단위 테스트와 Production 빌드부터 실행한다.
- 업종 매핑을 바꾸면 SECTOR_INDEX_MAP, exampleMarketData, 테스트, API_CHECK.md, README를
  같은 변경에서 갱신한다.
- 저장된 화면 모드는 컴퓨터 설정보다 우선한다.
- 병렬 작업은 worktree로 분리하고 통합은 메인 세션만 한다.
- 공식 매핑을 검증하지 못한 업종을 유사 지수나 임의 산식으로 채우지 않는다.
- 인증키를 기록하지 않고 로그인·결제·실제 계좌 연동을 구현하지 않는다.

문서를 고친 뒤 node --test lib/*.test.js와 npm test를 실행하고, 바뀐 파일과 판단 근거를
요약해줘. 커밋·push·배포는 하지 마.
```

완료 보고만 믿지 않고 Diff에서 데이터 결정, 계산 기준, 금지 규칙과 `.env.sample`의 키 이름을
직접 확인합니다. 실제 비밀값이 보이면 즉시 중단합니다.

## 6. 새 세션에서 같은 요청 다시 실행하기

AGENTS.md는 Codex를 시작할 때 읽히므로 `/new`만 쓰지 않습니다. 문서가 저장된 상태에서
Codex를 완전히 종료하고 프로젝트 폴더에서 다시 실행한 뒤, 4번과 같은 요청을 한 글자도
바꾸지 않고 보냅니다.

```text
업종 히트맵에 빠져 있는 업종들이 있네. 채워줄 수 있어?
```

실제 after 실험에서는 새 세션이 AGENTS.md에서 README와 API_CHECK.md를 확인하는 순서를
찾았습니다. 최신 공식 지수 목록을 다시 대조한 뒤 조선·게임·2차전지만 정확한 테마지수로
추가하고, 화장품은 임의 값 없이 계속 제외했습니다. 매핑, 실패용 예시 데이터, 테스트,
API_CHECK.md와 README도 함께 맞췄습니다. 최종 결과는 11개 타일, 단위 테스트 14개와
Production 빌드 통과였습니다.

## 7. 공유 전 최종 점검과 인계 글 만들기

코드를 커밋하기 전에 다음 순서로 검증합니다.

```text
$verify-market-dashboard
/diff
/review
```

검증하지 못한 배포나 Git 상태는 `PASS`로 바꾸지 않습니다. 실제 실험에서는 배포하지 않았기
때문에 최종 판정이 `BLOCKED`로 남았습니다. 로컬 테스트 통과와 배포 확인은 서로 다른
증거입니다.

검증 결과와 Diff, Review를 사람이 확인한 뒤에만 다음 요청을 보냅니다.

```text
지금 확인한 변경만 커밋해줘. 커밋 메시지에는 무엇을 바꿨는지와 함께, 공식 근거가 있는
세 업종만 추가하고 화장품 임의 산식을 제외한 이유를 남겨줘. push와 배포는 하지 마.
```

마지막으로 PR 설명은 Review와 별도로 요청합니다.

```text
이번 변경을 처음 보는 사람이 이해할 수 있게 PR 설명 초안을 써줘.
작업 내용, 결정과 이유, 검증 결과, 아직 확인하지 못한 항목, 리뷰어가 볼 지점을 구분해줘.
```
