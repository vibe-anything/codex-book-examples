# 국토교통부 아파트 매매 실거래가 자료 API

> 최종 확인일: 2026-07-17 / 공공데이터포털 데이터 수정일: 2025-07-04

이 문서는 공공데이터포털의 **국토교통부_아파트 매매 실거래가 자료**를 이 프로젝트에서 사용할 때 필요한 내용을 정리한다. 이 API는 「부동산 거래신고 등에 관한 법률」에 따라 신고된 아파트 매매 정보를 법정동 코드 앞 5자리와 계약년월로 조회한다.

공공데이터포털의 메타데이터와 Swagger 명세는 서로 갱신 시점이 다를 수 있다. 구현 전에는 [아파트 매매 실거래가 자료 공식 페이지](https://www.data.go.kr/data/15126469/openapi.do)의 수정일과 상세 기능을 다시 확인한다.

## 일반 자료와 상세 자료

공공데이터포털에는 이름이 비슷한 API가 따로 등록되어 있다.

| 구분 | 데이터 번호 | 서비스 경로 |
| --- | --- | --- |
| 아파트 매매 실거래가 자료 | `15126469` | `/1613000/RTMSDataSvcAptTrade` |
| 아파트 매매 실거래가 상세 자료 | `15126468` | `/1613000/RTMSDataSvcAptTradeDev` |

이 프로젝트는 아파트명, 법정동, 거래금액, 전용면적, 층, 계약일, 건축연도를 표시하므로 일반 자료 API만으로 기본 화면을 구성할 수 있다. 상세 자료를 사용하려면 [상세 자료 공식 페이지](https://www.data.go.kr/data/15126468/openapi.do)에서 별도로 활용 신청하고 응답 명세를 확인한다. 두 API는 인증 권한과 URL이 서로 다르므로 혼용하지 않는다.

## 요청 주소

```text
https://apis.data.go.kr/1613000/RTMSDataSvcAptTrade/getRTMSDataSvcAptTrade
```

공식 Swagger에는 HTTP와 HTTPS가 모두 표시되지만, 인증키 보호를 위해 HTTPS를 사용한다.

### 요청 파라미터

2026-07-17에 확인한 공식 Swagger의 요청 파라미터는 다음 세 개다.

| 이름 | 필수 | 형식 | 설명 | 예시 |
| --- | --- | --- | --- | --- |
| `serviceKey` | 필수 | 문자열 | 공공데이터포털에서 발급받은 인증키 | 발급받은 키 |
| `LAWD_CD` | 필수 | 숫자 5자리 | 법정동 코드 10자리 중 시군구를 나타내는 앞 5자리 | `11680` |
| `DEAL_YMD` | 필수 | 숫자 6자리 | 계약년월 `YYYYMM` | `202401` |

`LAWD_CD`는 행정표준코드관리시스템의 법정동 코드를 기준으로 한다. 예를 들어 서울특별시 강남구는 `11680`이다. 행정구역 개편으로 코드가 바뀔 수 있으므로 코드를 장기간 고정 데이터로 관리한다면 최신 코드와 주기적으로 대조한다.

현재 공식 Swagger에는 `pageNo`와 `numOfRows`가 **요청 파라미터로 등록되어 있지 않다**. 다만 응답 본문에는 `pageNo`, `numOfRows`, `totalCount`가 정의되어 있다. 이 프로젝트가 받는 `pageNo`와 `numOfRows`는 앱 내부 조회 조건과 응답 크기 제어용으로 구분하고, 실제 공공 API에 전달할지는 향후 공식 명세가 변경되었는지 확인한 뒤 결정한다.

### 호출 예시

```bash
curl --get \
  'https://apis.data.go.kr/1613000/RTMSDataSvcAptTrade/getRTMSDataSvcAptTrade' \
  --data-urlencode "serviceKey=${PUBLIC_DATA_API_KEY}" \
  --data-urlencode 'LAWD_CD=11680' \
  --data-urlencode 'DEAL_YMD=202401'
```

위 예시는 디코딩된 인증키를 `PUBLIC_DATA_API_KEY`에 저장하고 `curl`이 URL 인코딩하도록 하는 방식이다. 공공데이터포털에서 제공한 URL 인코딩 키를 그대로 URL에 붙이는 경우에는 다시 인코딩해 `%`가 `%25`로 바뀌지 않도록 주의한다.

## 응답 구조

정상 응답은 XML이며 최상위 구조는 다음과 같다.

```text
response
├── header
│   ├── resultCode
│   └── resultMsg
└── body
    ├── items
    │   └── item (거래별 반복)
    ├── totalCount
    ├── numOfRows
    └── pageNo
```

`header.resultCode`와 `header.resultMsg`를 먼저 확인한 다음 `body.items.item`을 읽는다. HTTP 상태가 200이어도 XML 본문에 인증 또는 업무 오류가 담길 수 있으므로 HTTP 상태만으로 성공을 판단하지 않는다.

## 데이터 변환 규칙

### 거래금액

`dealAmount`는 만원 단위 문자열이다. 쉼표와 공백을 제거한 뒤 만원 단위 숫자로 저장한다.

```js
const amountInTenThousands = Number(dealAmount.replaceAll(',', '').trim());
```

예를 들어 `"245,000"`은 내부에서 `245000`으로 다룬다. 화면에는 `24억 5,000만 원`처럼 억/만 원 단위로 표시한다.

### 계약일

계약일은 `dealYear`, `dealMonth`, `dealDay`를 조합해 `YYYY-MM-DD` 형식으로 정규화한다. 월과 일이 한 자리로 내려올 가능성을 고려해 두 자리로 채운다.

### 해제 거래

`cdealType` 또는 `cdealDay`에 값이 있는 거래는 계약이 해제된 건일 수 있다. 일반 거래와 합산하기 전에 제외할지, 해제 거래임을 화면에 표시할지 제품 정책을 정해야 한다. 단순히 최신 응답에 포함되었다는 이유로 유효 거래로 간주하면 통계가 왜곡될 수 있다.

### XML 파싱

조회 결과가 한 건일 때와 여러 건일 때 XML 파서가 `item`을 객체 또는 배열로 다르게 변환할 수 있다. 서버에서 항상 배열로 정규화한 뒤 화면용 필드로 매핑한다. 선택 필드는 빈 문자열이나 누락 상태를 허용한다.

## 이 프로젝트와의 연결

브라우저가 공공 API를 직접 호출하지 않고 Next.js 서버 라우트가 대신 호출한다.

```text
브라우저
  → GET /api/transactions?regionCode=11680&dealYmd=202401
  → Next.js 서버
  → 국토교통부 공공 API
  → XML 파싱·정규화
  → 프로젝트 JSON 응답
```

프로젝트 쿼리와 공공 API 파라미터의 대응은 다음과 같다.

| 프로젝트 | 공공 API | 비고 |
| --- | --- | --- |
| `regionCode` | `LAWD_CD` | 숫자 5자리 검증 |
| `dealYmd` | `DEAL_YMD` | `YYYYMM` 검증 |
| `pageNo` | 현재 공식 요청 명세에 없음 | 앱 내부 페이지 조건 |
| `numOfRows` | 현재 공식 요청 명세에 없음 | 앱 내부 결과 수 제한 |

현재 [`lib/transactions.js`](./lib/transactions.js)의 `fetchTransactions`는 샘플 데이터를 반환한다. 실 API 연동 시 이 함수 안에서 서버 환경변수, 공공 API 호출, XML 파싱, 상태 변환을 처리하고 [`app/api/transactions/route.js`](./app/api/transactions/route.js)는 프로젝트 JSON 계약을 유지한다.

## 인증키 설정과 보안

공공데이터포털에서 로그인한 뒤 해당 API의 활용 신청을 완료하고 인증키를 발급받는다. 키는 프로젝트 루트의 `.env`에 서버 전용 환경변수로 둔다.

```dotenv
PUBLIC_DATA_API_KEY=발급받은_디코딩_인증키
```

- 인증키를 코드, 문서 예시, Git 커밋, 오류 로그에 넣지 않는다.
- `NEXT_PUBLIC_` 접두사를 사용하지 않는다. 이 접두사가 붙은 값은 브라우저 번들에 노출될 수 있다.
- 외부 요청 URL 전체를 로그로 남기면 쿼리 문자열의 `serviceKey`가 노출될 수 있으므로 마스킹한다.
- 인증키 누락은 외부 호출 전에 검사한다.

## 상태와 오류 처리

공공 API 응답을 그대로 화면에 전달하지 말고 프로젝트가 판별하기 쉬운 상태로 변환한다.

| 프로젝트 상태 | 판별 기준 | 화면 의미 |
| --- | --- | --- |
| `SUCCESS` | 정상 결과이고 거래가 1건 이상 | 조회 결과 표시 |
| `EMPTY` | 정상 결과지만 `totalCount`가 0이거나 거래 목록이 없음 | 조회 성공, 결과 없음 |
| `API_KEY_MISSING` | 서버 환경변수에 키가 없음 | 인증 설정 필요 |
| 인증 오류 상태 | 게이트웨이 또는 `header`가 키 오류·권한 오류를 반환 | 키 또는 활용 신청 확인 |
| `INVALID_INPUT` | 지역 코드, 계약년월 또는 앱 페이지 조건 검증 실패 | 입력값 수정 요청 |
| `API_REQUEST_FAILED` | 네트워크 오류, 비정상 응답, XML 파싱 실패, 그 밖의 상위 API 오류 | 잠시 후 재시도 안내 |

빈 결과는 오류가 아니다. 또한 인증 오류와 잘못된 입력을 모두 `API_REQUEST_FAILED`로 합치면 사용자가 해결 방법을 알 수 없으므로 별도 상태로 유지한다. 공공 API의 구체적인 결과 코드는 포털의 **오픈API 에러코드**와 실제 `resultCode`를 기준으로 매핑한다.

## 운영 시 주의사항

- 업데이트 주기가 실시간이라는 설명은 신고·정정 정보가 API에 즉시 확정된다는 보장을 뜻하지 않는다.
- 취소 또는 해제 정보가 나중에 반영될 수 있으므로 장기 저장 데이터는 주기적으로 다시 조회한다.
- 월 단위·시군구 단위 조회이므로 여러 지역이나 여러 달을 조회하면 호출 수가 빠르게 늘어난다.
- 호출량이 개발 계정 한도를 넘는다면 호출 간 캐시, 중복 요청 제거, 운영 계정 트래픽 증량을 검토한다.
- API 필드가 추가되어도 파서가 실패하지 않도록 필요한 필드만 선택해 매핑한다.
