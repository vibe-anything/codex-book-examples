# 15장 프롬프트

이 폴더는 `ch14`를 이어받아 아래 순서대로 진행한 결과다. 15장 본문(2026-08-02 개고본)의
요청문을 한 글자도 바꾸지 않고 codex 0.146.0에 넣었다. 키와 접속 정보 값은 대화나 코드에
넣지 않고 `.env`에만 넣으며, 이름만 남긴 `.env.sample`을 함께 둔다.

책 흐름과 다른 점 하나: 본문에서 테이블 생성과 적재는 Codex가 Supabase MCP 통로로
수행하지만, 이 재구축은 호스티드 계정 없이 로컬 스택(`supabase start`)을 썼다. Codex가
설계 요청에 제안한 SQL을 그대로 로컬 DB에 적용하고, 적재는 같은 권한 구도(service_role=
관리 통로, anon=앱 통로)로 하네스가 대역했다. 상세는 문서고 `ch15/build-log.md`에 있다.

## 1. 테이블 설계 (§15.4)

```
대시보드 데이터를 Supabase에 저장하려고 해. 테이블 구조를 설계해줘.

요구사항:
- 일별 시세: 종목코드, 종목명, 기준일, 종가, 등락률, 거래대금을 저장한다.
  같은 기준일의 같은 종목이 두 번 저장되는 일은 구조로 막아야 한다.
- 앱에서는 익명 방문자가 시세를 읽기만 할 수 있게 RLS를 켜고 읽기(SELECT) 정책만 만든다.
- 쓰기(INSERT, UPDATE, DELETE) 정책은 만들지 않는다. 시세 적재는 이 학습용 MCP로만 한다.
- 관심 종목은 localStorage에 남긴다. 사용자 계정과 관심 종목 테이블은 만들지 않는다.
- 아직 만들지 말고, 테이블 구조와 그렇게 정한 이유부터 보여줘.
```

> 이 실행의 제안: `daily_stock_prices`, 복합 기본 키 `(price_date, stock_code)`,
> RLS + anon SELECT 정책. 같은 요청이 별도 번호를 기본 키로 두고 두 값에 UNIQUE 제약을
> 거는 설계로 답해 오기도 한다(0.145 실측 3회 전부). 어느 쪽이든 중복은 구조가 막는다.

## 2. 적재와 이중 적재 실험 (§15.4)

본문 요청문은 Codex가 MCP로 적재하는 흐름이다. 이 재구축은 같은 데이터를 하네스가
로컬 스택에 두 번 적재해 재현했다: 기준일 2026-07-30 데이터 2,873행 → 같은 데이터
재적재 시 전량 중복 충돌, 행 수 2,873 그대로.

## 3. 화면 전환 (§15.5)

```
이제 대시보드가 Supabase를 읽게 바꾸자.
- 관심 종목은 지금처럼 localStorage에서만 읽고 써줘.
- 시세는 앞에서 만든 일별 시세 테이블의 최신 기준일 데이터를 읽어 보여주고,
  그 기준일을 화면에 함께 표시해줘.
- NEXT_PUBLIC_SUPABASE_URL과 NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY를 사용해.
- 앱에는 시세를 추가·수정·삭제하는 경로를 만들지 마.
- Supabase에 데이터가 없거나 읽기에 실패하면 기존 API를 호출하고,
  그것도 실패할 때만 예시 데이터와 안내를 보여줘.
```

> 이 실행의 결과: `lib/supabaseMarketData.js`(REST 직접 조회, supabase-js 미설치),
> 출처 배지("Supabase"/"공공데이터"/"예시 데이터")와 기준일 표시, Supabase 소스일 때
> 지수·업종 영역 숨김. 같은 요청이 supabase-js를 설치하는 구현으로 갈 수도 있다.

## 주의

- 14장 인증키 보호 훅은 이 장에서도 매 도구 호출 전에 검사를 돈다. 이 실행은 요청문에
  변수 이름이 있어 Codex가 `.env`를 읽을 일이 없었고 차단 없이 끝났다. `.env`를 읽으려는
  실행에서는 `PreToolUse hook (blocked)` 화면이 뜨고, Codex는 `process.env` 참조로 우회한다.
- `.env.sample`은 이 장부터 둔다(2026-08-02 저자 결정 — ch14 커밋의 "17장 처리"를 대체).
  값은 절대 넣지 않고 이름 세 개만 남긴다.
