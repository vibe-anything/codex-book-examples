# 16장 프롬프트 모음

아래 요청문은 `vibecoding-codex-book-examples/ch16` 폴더에서 Codex를 실행한 뒤, 장의 흐름에 맞춰 하나씩 복사해 붙여넣습니다.

이 장은 15장까지 만든 국내 시장 대시보드를 Vercel에 배포하고, 로컬과 배포 환경이 다르게 깨지는 지점을 확인합니다. 첫 배포에서는 실습을 위해 환경변수를 한 번만 비워 두고, 예시 데이터와 관심 종목 오류가 나타나는지 봅니다. 고치기 전 배포 주소는 다른 사람에게 공유하지 않습니다.

공공데이터포털과 Supabase의 실제 키 값은 Codex 대화나 이 파일에 붙여넣지 않습니다. 값은 로컬 `.env`와 Vercel 대시보드에 직접 입력합니다. 배포 로그를 Codex에게 읽힐 때도 인증키·토큰·쿠키·사용자 개인정보가 들어 있지 않은지 먼저 확인하고, 필요한 시간대와 오류만 조회합니다.

## 0. 작업 폴더에서 Codex 열기

```bash
cd vibecoding-codex-book-examples/ch16
codex
```

## 1. 배포 전 공개 점검하기

배포하기 전에 비밀값과 실행 상태를 먼저 확인합니다. 이 단계에서는 파일을 고치지 않습니다.

```text
이 프로젝트를 Vercel에 배포하기 전에 공개 점검을 해줘.

확인할 것:
- .env가 Git 추적 파일이나 커밋 기록에 들어 있지 않은지 확인한다.
- 추적 중인 소스와 설정 파일에 인증키·토큰·비밀번호 값이 직접 적혀 있지 않은지 확인한다.
- 비밀값처럼 보이는 내용을 발견해도 값을 출력하지 말고 파일 경로와 확인할 위치만 알려준다.
- npm test를 실행해 Next.js 빌드가 통과하는지 확인한다.
- 현재 변경 파일을 정리하고, 문제가 생겼을 때 어떤 커밋으로 되돌릴지 알려준다.

지금은 파일을 수정하거나 배포하지 말고 점검 결과만 보고해줘.
```

## 2. GitHub 저장소를 Vercel에 연결해 첫 배포하기

첫 배포는 Vercel 대시보드에서 진행합니다.

1. Vercel에서 `Continue with GitHub`로 가입하고 GitHub 접근 권한을 확인합니다.
2. New Project에서 이 예제 저장소를 찾아 Import를 누릅니다.
3. 이 저장소 전체를 연결한다면 Root Directory를 `ch16`로 지정합니다. `ch16`만 별도 저장소로 복사했다면 `./`를 그대로 둡니다.
4. Vercel이 Next.js 프로젝트로 인식했는지 확인합니다.
5. 누락 증상을 관찰하려고 Environment Variables는 이번 한 번만 비워 둔 채 Deploy를 누릅니다.
6. 배포 주소를 열어 화면의 `예시 데이터` 안내와 관심 종목 오류를 확인합니다. 고치기 전에는 주소를 공유하지 않습니다.

## 3. Vercel MCP 연결하기

첫 Codex 세션을 마친 뒤 터미널에서 Vercel 공식 MCP 서버를 추가하고 Codex를 다시 엽니다.

```bash
codex mcp add vercel --url https://mcp.vercel.com
codex
```

브라우저 승인 창이 열리면 주소가 `mcp.vercel.com`인지 확인합니다. 읽기·쓰기 권한 목록을 읽고, 배포한 프로젝트가 있는 팀을 선택한 뒤 승인합니다. 새 Codex 세션에서 `/mcp`를 실행해 `vercel` 연결과 도구 목록이 보이는지 확인합니다.

## 4. 배포 상태와 최근 로그로 원인 좁히기

```text
방금 Vercel에 배포한 대시보드가 예시 데이터로 돌고, 관심 종목도 안 떠.

Vercel MCP로 다음을 확인해줘.
- 방금 만든 프로젝트와 최신 프로덕션 배포를 찾는다. 프로젝트가 여러 개라 확실하지 않으면 먼저 물어본다.
- 최신 배포가 Ready인지 확인한다.
- 최근 30분의 프로덕션 런타임 로그에서 500 오류를 찾고, /api/watchlist 요청을 우선 살핀다.
- 화면의 예시 데이터 안내와 /api/watchlist 오류를 현재 코드의 환경변수 사용 부분과 맞춰 원인을 좁힌다.
- Vercel에 추가해야 할 환경변수 이름만 알려준다. 실제 값은 읽거나 출력하지 않는다.

코드와 Vercel 설정은 바꾸지 말고, 확인한 근거와 내가 직접 해야 할 작업만 보고해줘.
```

정상이라면 Codex는 배포 자체는 Ready이지만, 다음 환경변수가 배포 환경에 없다고 알려 줍니다.

- `DATA_GO_KR_SERVICE_KEY`
- `SUPABASE_URL`
- `SUPABASE_ANON_KEY`

## 5. 환경변수를 넣고 재배포하기

Vercel 프로젝트의 Settings → Environment Variables에서 세 이름을 추가합니다. 값은 로컬 `.env`를 보고 Vercel 입력란에 직접 넣으며, Codex 대화에는 붙여넣지 않습니다. 이 실습의 첫 배포는 프로덕션이므로 Production 환경에 적용합니다. 프리뷰 배포를 따로 쓴다면 Preview 환경에도 필요한 값을 별도로 설정해야 합니다.

환경변수는 이미 실행 중인 배포에 자동으로 들어가지 않습니다. 저장 뒤 Vercel이 표시하는 Redeploy를 눌러 새 배포를 만듭니다.

## 6. Codex에게 재배포 결과 확인시키기

```text
재배포가 끝났으면 Vercel MCP로 최신 프로덕션 배포를 확인해줘.

확인할 것:
- 최신 배포 상태가 Ready인지 확인한다.
- 배포 주소를 직접 열어 화면의 '예시 데이터' 문구가 실제 데이터 출처 안내로 바뀌었는지 본다.
- 관심 종목 두 개가 오류 없이 표시되는지 확인한다.
- /api/watchlist가 200으로 응답하고 종목 코드를 돌려주는지 확인한다.
- 최근 런타임 로그에서 같은 /api/watchlist 500 오류가 다시 생기지 않았는지 확인한다.

저장소 파일과 Vercel 설정은 바꾸지 말고, 확인 결과와 남은 문제만 보고해줘.
```

Codex의 보고만 믿고 끝내지 않습니다. 배포 주소를 직접 열어 기준일, 실제 데이터 출처 안내, 관심 종목을 눈으로 확인합니다. 가능하면 시크릿 창이나 휴대폰에서도 한 번 더 엽니다.

## 7. Vercel MCP를 더 활용해 보기 (선택)

로그가 많을 때는 범위를 좁혀 요청합니다.

```text
Vercel MCP로 이 프로젝트의 최근 1시간 프로덕션 런타임 로그를 확인해줘.
500 오류만 보고, 경로·발생 시각·반복 횟수·가능한 원인을 정리해줘.
로그에 비밀정보나 사용자 개인정보가 보이면 그대로 출력하지 말고 종류와 위치만 알려줘.
```

Vercel 기능이 헷갈릴 때는 모델의 기억 대신 공식 문서를 검색하게 합니다.

```text
Vercel MCP의 문서 검색 도구로 Production과 Preview의 환경변수 적용 차이를 찾아줘.
현재 공식 문서 기준으로 세 문장 안에 설명하고, 확인한 공식 문서 URL을 함께 남겨줘.
```
