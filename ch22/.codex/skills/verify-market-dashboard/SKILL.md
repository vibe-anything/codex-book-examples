# Verify Market Dashboard

공유 직전의 프로덕션 상태를 읽기 전용으로 검증하고 `PASS`, `WARNING`, `BLOCKED`로 보고하라.

## 시작

1. 저장소 루트에서 [references/market-dashboard-criteria.md](references/market-dashboard-criteria.md)를 끝까지 읽고 앱별 완료 기준을 적용하라.
2. 아래 다섯 검증을 지정된 순서대로 수행하라. 한 항목이 실패해도 안전하게 확인할 수 있는 다음 항목은 계속하라.
3. 사용자가 공유 대상 커밋을 지정했으면 이를 전체 commit SHA로 해석하라. 지정하지 않았으면 작업 트리가 깨끗할 때만 `HEAD`를 사용하라. 작업 트리가 더러우면 1번을 `BLOCKED`로 판정하되 나머지는 계속하라.
4. 저장소의 Vercel 프로젝트 연결 정보는 읽을 수 있지만 새로 연결하거나 수정하지 마라.

## 도구

- Vercel 조회(프로젝트 정보, 배포 상태, 배포 상세의 Git SHA, 대표 주소, 런타임 로그)는 이미 연결된 Vercel MCP만 사용하라. 다른 도구를 설치하거나 로그인해서 보완하지 마라.
- 화면·API 확인은 프로젝트의 Production 대표 주소(alias)를 기준으로 하라. 불변 배포 URL은 Deployment Protection이 켜져 있으면 로그인이 필요해 화면 판정 기준으로 쓰지 마라.
- 이 앱은 서버 렌더링이라 대표 주소의 응답 HTML이 곧 화면이다. 인앱 브라우저를 쓸 수 있으면 최종 렌더링까지 확인하고, 없으면 GET 응답 HTML로 판정하라.
- MCP나 네트워크로 확인할 수 없는 항목은 PASS로 만들지 말고 앱별 기준에 따라 `WARNING`이나 `BLOCKED`로 남기며 사람이 할 확인을 안내하라.

## 안전 제한

- 코드, 파일, Git, Vercel, 데이터베이스를 수정하지 마라. 자동 수정, 배포, 재배포, promote, rollback, alias 변경, 환경변수 변경을 하지 마라.
- 환경변수 값을 조회·출력하지 마라. Vercel에 등록된 환경변수 조회를 시도하지 마라. 로컬 실환경 `.env*` 파일을 열거나 출력하지 마라. 이름 목록만 담긴 `.env.sample`은 읽어도 된다.
- 배포 앱에는 `GET` 또는 `HEAD`만 보내라. `/api/watchlist`의 `POST`와 `DELETE`는 데이터를 바꾸므로 호출하지 마라.
- 로그 원문, 요청 쿼리, 응답의 인증 헤더, 탐지된 비밀값을 출력하거나 보고서에 복사하지 마라. 경로, 상태 코드, 횟수, 짧은 비가역 지문만 남겨라.
- 비밀 검사를 위해 파일 내용을 처리할 때도 값은 프로세스 내부에서만 판별하고 출력은 `<redacted>` 메타데이터로 제한하라.

## 검증 순서

### 1. 배포 상태

Vercel MCP로 프로젝트의 가장 최신 Production 배포를 찾고 상태, 생성 시각, 배포 URL, 대표 주소(alias), 배포 Git commit SHA를 조회하라. 최신 배포가 `READY`이고 배포 SHA가 공유 대상 전체 SHA와 정확히 같은지 확인하라. Production 여부나 SHA를 추정하지 마라.

### 2. 배포 화면·API

프로젝트의 Production 대표 주소를 직접 열어 최종 화면의 제목, 데이터 출처, 기준일을 확인하라. 대표 주소가 1번에서 확인한 최신 Production 배포를 가리키는지 함께 확인하고, 다른 배포를 가리키면 그 사실을 보고하라.

대표 주소와 같은 origin의 `GET /api/watchlist`를 호출해 HTTP 200과 JSON `{ "codes": [...] }` 형태를 확인하라. 응답 배열의 실제 데이터는 보고하지 마라. 로그인·보호 화면으로 열리면 앱 오류가 아니라 접근 차단으로 판정하라.

### 3. 런타임 로그

Vercel MCP로 최신 배포의 최근 24시간 Production 런타임 로그를 조회하라. 배포 후 24시간이 지나지 않았으면 배포 시각부터 현재까지를 관찰 구간으로 사용하라.

5xx를 경로, 상태 코드, 오류 지문으로 묶어 횟수만 집계하라. 원문 메시지는 보고서에 싣지 마라.

### 4. 환경변수 계약

이 검증의 기준은 저장소에 적힌 계약이다. 공유 대상 커밋의 코드에서 `process.env` 접근(`process.env.NAME`, `process.env[이름상수]`)과 환경변수 이름 상수 선언을 검색해 코드가 요구하는 이름 집합을 만들고, 저장소의 계약 — `.env.sample`의 이름 목록과 앱별 기준의 필수 이름 — 과 대조하라.

- 코드가 계약에 없는 이름을 요구하면 `BLOCKED`로 판정하라. 기존 이름의 오타 가능성을 함께 진단하고, 의도한 새 변수라면 계약 갱신과 Vercel Production 등록 확인을 다음 행동으로 안내하라.
- 계약에는 있는데 코드가 더 이상 쓰지 않는 이름은 `WARNING`으로 보고하라.
- 값의 조회, 유효성 검사, 출력은 하지 마라. Vercel에 등록된 이름 조회는 이 Skill의 범위 밖이다. 등록된 변수가 실제로 작동하는지의 간접 증거는 2번의 실제 데이터 출처 표시다.

### 5. Git 비밀 검사

`python3 .codex/skills/verify-market-dashboard/scripts/scan_git_secrets.py --repo .`를 실행하라. 이 스크립트는 현재 추적 파일과 모든 reachable commit의 파일명·blob을 읽기 전용으로 검사하고, 매치 값을 출력하지 않는다. 스크립트 파일을 먼저 읽어 비노출 동작이 유지되는지 확인한 뒤 사용하라.

스크립트를 실행할 수 없으면 동일한 비노출 보장을 갖춘 대안을 사용하라. `git grep`처럼 매치 원문을 터미널에 출력하는 명령은 사용하지 마라. 전체 이력을 안전하게 검사할 수 없으면 앱별 기준에 따라 판정하라.

## 판정과 보고

- `PASS`: 완료 기준을 충분한 증거로 확인함.
- `WARNING`: 확인하지 못한 항목이 있거나 비차단 우려가 있음. 확인하지 못한 것을 `PASS`로 계산하지 마라.
- `BLOCKED`: 필수 조건이 실패했거나 필수 증거를 안전하게 확인할 수 없음.

전체 판정은 가장 심각한 상태를 따르라: `BLOCKED`가 하나라도 있으면 전체 `BLOCKED`, 그 외 `WARNING`이 하나라도 있으면 전체 `WARNING`, 다섯 항목이 모두 `PASS`일 때만 전체 `PASS`이다.

보고는 매번 같은 형식으로 하라. 영역 이름과 행 순서를 바꾸지 마라.

```markdown
전체: PASS | WARNING | BLOCKED

| 영역 | 상태 | 확인한 근거 | 다음 행동 |
| --- | --- | --- | --- |
| 배포 상태 | ... | ... | ... |
| 배포 화면·API | ... | ... | ... |
| 런타임 로그 | ... | ... | ... |
| 환경변수 계약 | ... | ... | ... |
| Git 비밀 검사 | ... | ... | ... |

- 공유 대상 SHA: ...
- 배포 SHA: ...
- 대표 주소: ...
- 로그 관찰 구간: ...
```

환경변수 값, 로그 원문, 비밀 탐지 매치 내용을 보고서에 포함하지 마라.
