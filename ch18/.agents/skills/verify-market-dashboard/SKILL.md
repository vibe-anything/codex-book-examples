# 시장 대시보드 공유 전 최종 검증

다섯 영역을 아래 순서대로 검증하고 사실로 확인한 근거만 보고한다.

## 불변 규칙

- 시작할 때 [앱별 완료 기준](references/app-completion-criteria.md)을 끝까지 읽고 적용한다.
- 모든 검증을 읽기 전용으로 수행한다. 코드·문서·설정·Git 상태를 수정하거나 자동 수정, 커밋, 푸시, 배포, 재배포를 하지 않는다.
- 환경변수 값이나 Vercel 환경변수 목록·값을 조회하거나 변경하지 않는다. `.env.sample`에서는 이름만 읽고 다른 `.env` 계열 파일의 내용은 열지 않는다.
- Vercel의 배포 상태, 주소, 런타임 로그, 배포 화면·응답은 현재 연결된 Vercel MCP로만 조회한다. 웹 검색, 범용 브라우저, `curl`, Vercel CLI, 직접 HTTP 클라이언트, 다른 커넥터로 보완하지 않는다.
- Vercel MCP가 없거나 필요한 기능이 없으면 설치·로그인·연결을 시도하지 않는다. 해당 영역을 `WARNING`으로 판정하고 사람이 Vercel 대시보드에서 확인할 구체적인 항목을 `다음 행동`에 적는다.
- 비밀 검사 중 발견한 값은 도구 출력이나 보고서에 복사하지 않는다. 유형, 파일 경로, 줄 번호, 커밋·blob 식별자만 기록한다.
- 확인하지 못했거나 근거가 모호한 항목을 `PASS`로 판정하지 않는다.

## 준비

1. `git rev-parse --show-toplevel`로 저장소 루트에서 실행 중인지 확인한다.
2. 사용자가 공유 대상 커밋을 지정했으면 그 전체 SHA를 사용한다. 지정하지 않았으면 실행 시점의 `git rev-parse HEAD` 전체 SHA를 사용하고 이 선택을 배포 상태 근거에 명시한다.
3. `git status --short`, 현재 브랜치, 대상 SHA를 읽기 전용으로 확인한다. 대상 커밋이 존재하지 않으면 배포 상태를 `BLOCKED`로 판정하되 나머지 검증은 가능한 범위에서 계속한다.
4. Vercel MCP의 프로젝트·배포 메타데이터로 현재 저장소와 연결된 프로젝트를 식별한다. 후보가 둘 이상이면 추측하지 말고 Vercel 관련 영역을 `WARNING`으로 판정한다.

## 검증 순서

### 1. 배포 상태

Vercel MCP에서 식별한 프로젝트의 최신 프로덕션 배포 하나를 조회한다. Preview나 과거 Ready 배포로 대체하지 않는다. 배포 ID, 생성 시각, 상태, 프로덕션 주소, 원본 Git 커밋 SHA를 확인한다.

- 최신 프로덕션 배포 상태가 `Ready`이고 원본 SHA가 대상 SHA와 정확히 같을 때만 `PASS`로 판정한다.
- 상태가 Ready가 아니거나 확인된 SHA가 다르면 `BLOCKED`로 판정한다.
- 상태나 원본 SHA를 MCP에서 확인할 수 없으면 `WARNING`으로 판정한다.

### 2. 배포 화면·API

1단계에서 얻은 프로덕션 주소를 Vercel MCP로 직접 연다. 앱별 완료 기준의 화면·실제 시세 조건을 모두 확인한다. 단순 HTTP 200이나 정적 제목만으로 통과시키지 않는다.

- 실제 데이터 출처, 유효한 기준일, 식별 가능한 종목의 종가·등락률을 모두 확인하면 `PASS`로 판정한다.
- `예시 데이터`가 표시되거나 필수 표시가 누락되거나 화면·응답이 5xx이면 `BLOCKED`로 판정한다.
- MCP가 화면 또는 응답 내용을 읽지 못하거나 일부 조건만 확인할 수 있으면 `WARNING`으로 판정한다.

### 3. 런타임 로그

최신 프로덕션 배포를 대상으로 배포 시각과 검증 시각 중 최근 24시간이 겹치는 구간을 조회한다. MCP가 다른 범위만 지원하면 실제 조회 범위를 근거에 정확히 적는다. HTTP 500~599를 세고 경로·상태·오류 지문별로 묶되 요청 본문, 헤더, 토큰 같은 민감 정보는 기록하지 않는다.

- 조회가 성공하고 5xx가 0건이면 `PASS`로 판정한다.
- 동일 경로 또는 동일 오류 지문의 5xx가 2회 이상이면 반복 오류로 보고 `BLOCKED`로 판정한다.
- 5xx가 1건이거나 서로 다른 일회성 5xx만 있으면 `WARNING`으로 판정한다.
- 로그 기능이나 충분한 시간 범위를 확인하지 못하면 `WARNING`으로 판정한다.

### 4. 환경변수 계약

값을 읽지 말고 이름 집합만 비교한다.

1. `.env.sample`의 키 이름을 읽는다.
2. 앱별 완료 기준의 환경변수 계약 표를 읽는다.
3. 기준 문서에 정의된 앱 코드 범위에서 정적·동적 `process.env` 참조와 빌드·런타임 설정의 환경변수 이름을 찾는다. 상수에 저장한 이름도 실제 문자열까지 추적한다.
4. 세 집합을 비교하고 근거에는 이름만 기록한다.

세 집합이 정확히 같을 때만 `PASS`로 판정한다. 코드가 계약에 없는 이름을 요구하거나 `.env.sample`, 앱별 기준 문서, 코드의 집합이 다르면 `BLOCKED`로 판정한다. 동적으로 계산되어 이름을 확정할 수 없으면 `WARNING`으로 판정한다.

### 5. Git 비밀 검사

저장소 루트에서 다음 읽기 전용 스크립트를 실행한다.

```bash
python3 .agents/skills/verify-market-dashboard/scripts/scan_git_secrets.py
```

스크립트는 현재 Git 추적 파일, 인덱스 blob, 모든 도달 가능한 커밋 이력의 파일명·텍스트 blob·커밋 메시지를 검사하며 발견한 비밀값 자체는 출력하지 않는다.

- 종료 코드 0이고 결과가 `PASS`이면 `PASS`로 판정한다.
- 금지된 `.env` 계열 파일 또는 비밀 패턴이 발견되어 결과가 `BLOCKED`이면 `BLOCKED`로 판정한다.
- 얕은 clone, 너무 큰 blob, Git 읽기 실패 등으로 결과가 불완전해 `WARNING`이면 `WARNING`으로 판정한다.

스크립트를 실행할 수 없을 때 임의의 수동 검색으로 `PASS`를 만들지 말고 `WARNING`으로 남긴다.

## 판정 합산

- 한 영역이라도 `BLOCKED`이면 전체 판정을 `BLOCKED`로 정한다.
- `BLOCKED`가 없고 하나라도 `WARNING`이면 전체 판정을 `WARNING`으로 정한다.
- 다섯 영역이 모두 `PASS`일 때만 전체 판정을 `PASS`로 정한다.
- 선행 단계가 실패해 후속 Vercel 확인을 못 한 경우 후속 영역은 `PASS`가 아니라 `WARNING`으로 정한다. 로컬에서 독립적으로 가능한 4·5단계는 계속 수행한다.

## 보고 형식

보고서는 한국어로 작성하고 아래 한 줄과 다섯 행 표만 출력한다. 행 이름과 순서를 바꾸거나 다른 절을 덧붙이지 않는다. 각 근거에는 확인 시각·범위, 배포 ID·주소·SHA, 오류 건수, 환경변수 이름, 검사 범위를 필요한 만큼만 적고 비밀값은 적지 않는다. `WARNING`과 `BLOCKED`의 다음 행동은 사람이 수행할 확인·조치로 구체화하며 자동 수행하지 않는다. `PASS`의 다음 행동은 `없음`으로 적는다.

```markdown
전체 판정: PASS|WARNING|BLOCKED

| 영역 | 상태 | 확인한 근거 | 다음 행동 |
| --- | --- | --- | --- |
| 배포 상태 | PASS|WARNING|BLOCKED | ... | ... |
| 배포 화면·API | PASS|WARNING|BLOCKED | ... | ... |
| 런타임 로그 | PASS|WARNING|BLOCKED | ... | ... |
| 환경변수 계약 | PASS|WARNING|BLOCKED | ... | ... |
| Git 비밀 검사 | PASS|WARNING|BLOCKED | ... | ... |
```
